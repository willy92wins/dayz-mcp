- Expansion AI adapter (90f9): new read-only tool `ai_group_state(group_id=None, scene_id=None)` reads one adapter group (`ai_group`) or every group of a scene (`ai_groups`) from the optional `@DayZ_MCP_ExpansionAI` PBO, with no lease. Per member it reports `alive`, `pos`, `health`, `fsm_state`/`fsm_substate` (null FSM references read empty), `threat` (`GetThreatToSelf(true)`), `fighting`, both movement-speed limits, `emote_playing` and `emote_pending` (Expansion and vanilla layers); a gone member answers `gone` with its last observation marked `last_observation`. Per group it reports faction, formation, `formation_state`, `behaviour` in both vocabularies, waypoint index/count and current waypoint, `in_combat`, `alive`, `members_total`, and for a releasing group with anything left `release: "pending"` with the pending ids and `group_present`, without calling getters of a group Expansion no longer returns (`eAIGroup.GetGroupByID(id, false)`). Unknown or fully released groups are `not_found`; a group with no living members answers ok with `alive: 0`. The verb joins the `&xai` bitmask at bit 3 (append-only; the announced mask covers only the verbs the adapter dispatches). The broker admits the verb by census/`ach`/verb/`xai` only (never the lease-close gate), so residues stay readable on a census that announces no close support (a real bridge v12 peer is stopped earlier by the version gate). In a run launched by `dayz_test_run`, after `session_release` (`RUNNING_IDLE`), `ai_group_state` answers `run_not_owned` until a lease adopts the run (then it reads again without a token: `loopback.py` `_enqueue_run_rejection` lets a `RUNNING` run through); `session_status` (`lease_end.unconfirmed`) only says the close owes the release of some group (`ai_group_release_unconfirmed`), not which ones nor in what state; the groups' state is read before the release. Outside a managed run, the read still needs no lease. The read joins the compact pre-lease catalog beside `chat_read` (0205); to keep that listing under its 23 000-byte ceiling, its input schemas drop the `title` annotations Pydantic generates from field names (about 4 KB; the listing is now about 19 KB), and every field, type, default, bound and description stays, as do the titles of the full listing after a lease. Offline tests: `tools/tests/test_xai_group_state.py` (O4, E7, O13 residue part) and `tools/tests/test_progressive_disclosure.py` (the compact listing without the generated titles). Requires a PBO built from this release with Expansion AI loaded; in-game validation is pending.
- Expansion AI adapter `ai_group_order` (3ca5, on top of 173a). New lease-required tool `ai_group_order` orders one group registered by `ai_group_spawn`, with a lease, on the server: at least one of `behaviour`, `waypoints`, `formation` or `speed` (none is `bad_args` and sends nothing). The adapter validates every field before applying any — `behaviour` (HOLD, ONCE, LOOP, ROAM), `formation` (a name registered in `eAIFormation.s_FormationTypes` of the installed Expansion build, so a newer build's formation is accepted and `RANDOM` is refused), `waypoints` (flat triples, 1 to 32 points; an empty list is refused at the tool, the broker schema and the bridge) and `speed` (1 to 3, only beside `speed_set`) — so a bad formation changes nothing, not even the other fields. Only the fields present are applied: waypoints replace the route, HOLD is formation NONE plus HALT with saved speed preferences (a repeated HOLD touches neither, a speed ordered in a HOLD is only saved, leaving a HOLD restores them), and a formation change keeps the previous scale and looseness. The reply is read after the change (`ai_group`: `group_id`, `behaviour`/`behaviour_expansion`, `formation`, `formation_state`, `waypoint_count`, `waypoint_index`, `in_combat` and `combat_may_override` in combat, `roams_expansion_locations` for ROAM, member `speed_limit`s); an unknown or `releasing` group answers `not_found` with no `ai_group`. The verb joins the `&xai` bitmask at bit 2 (append-only; the announced mask covers only the verbs the adapter dispatches: release, spawn, order) and, as a new mutation, stays inert behind the all-peers lease-close gate until v13. Tests: `tools/tests/test_xai_group_order.py` (O3, O4, E5 for this verb, O1/O2/O7 branches, two Enforce mutants) plus the catalog, census and count gates its verb feeds. **Requires a new adapter PBO; in-game validation is pending.**

### Fixed

- #363 follow-up (Enfusion review L1/L2/C2, adversarial review S1/S2/N1, NIT-1). `player_look_at`'s server copy (`addon/scripts/4_World/MCP_LookAt.c`): the server accepts a look only on a harness `profile=test` server (`MCPLookAtControl.SetServerAllowed`, set in `MissionServer.OnMissionStart` from the godmode default `MCPBridge.ConfigIsTestProfile()` just set, so the config is still read once); elsewhere the look's message, start or release, is consumed unread in `OnInputUserDataProcess` and logs nothing (L2b), so a client cannot turn its own server heading with that message nor fill the server's script log with it. There is no admin route: no other sender, admin or not, can turn a body. The sender is always the player turned (the engine hands a client's input user data to the server copy of the player it controls); a start within `SERVER_MIN_START_INTERVAL_S` (0.1 s) of that sender's last one is refused `throttled`. The owner sends no start sooner than `OWNER_MIN_START_INTERVAL_S` (0.5 s, five times the server's) after its last one, and forgets that time if the tick clock went back (a new game in the same process): `player_look_at` then answers `input_busy` and turns neither side, so two starts the owner sent are throttled by the server only if the network compresses their arrivals by more than 0.4 s (0.25 s server interval before: arrivals 0.2 s apart were throttled and the owner turned alone). An accepted start no longer prints a script-log line, and the same refusal, or the same ignored release, repeated in a row is printed once. While a look still turns the player (`MCPLookAtControl.IsRunning()`: begun, not finished), `player_move` and `weapon_aim` answer `busy` before anything starts (L1b). The way to turn is picked once, by the owner at `Begin` from its camera (`StartTurnSign`/`TurnSignFor`, a tie within `TIE_BAND_DEG`, 2°, of 180° broken right), and sent in the start (one more `int`, refused `bad_turn` outside -1..1); both the owner's camera pulse and the server's heading pulse hold it through `LatchDeg` while the target is more than `LATCH_FROM_DEG` (90°) off, so two readings a little apart near 180° (owner -177.9°, server -178.1°) no longer turn the two sides opposite ways. An accepted `player_move` ends the look's server copy (`MCPLookServerRelease("move_started")` in `MCPMoveAccept`) and `weapon_aim` ends a converged look's copy first (`MCPLookAtControl.ReleaseServerCopy()` in `DispatchWeaponAim`), so the server stops turning the heading under them instead of running on up to its band or deadman (budget + 0.5 s). The `input_busy` comments of `Begin`, `SendServerStart`, `FlushServerRelease` and `DispatchPlayerLookAt` now say that a previous look's pending release may still leave before the start is refused. `object_set_health` and `telemetry_read` (c703) read health only through `HealthReadable` (`MCPBridge.c`): besides the `DamageSystem` class, the config must have `DamageSystem GlobalHealth` (`GetGame().ConfigIsExisting` by full path under `CfgWeapons`/`CfgMagazines`/`CfgVehicles`, as vanilla `InitDamageZoneDisplayNameMapping`, `entityai.c:398-413`), checked before `GetDamageZones`, and an `EntityAI` must be past its `DeferredInit` (`IsInitialized`, `entityai.c:240`, `:277-285`); a `Land_` building is an `EntityAI` (`Building : EntityAI`) and takes the full check; a tree or another plant (`Plant : Object`) keeps the `DamageSystem` test alone, as before; otherwise `object_set_health` answers `no_health` and `telemetry_read` leaves `health01` at 0. Tests: `LookMirrorTieBreakTest`, `LookMirrorLatchTest`, `LookMirrorStartIntervalTest`, `LookMirrorGateTest`, `LookMirrorInputGateTest`, `LookMirrorBusyTest`, `LookMirrorMoveAndAimReleaseTest` in `tools/tests/test_player_look_mirror.py`; `test_g6`-`test_g10`, `test_t3` and `test_t4` in `tools/tests/test_fb_c703_object_set_health.py`; each fails on the code before this change. When it is missing or different, `bridge_status` reports `capabilities.state=mismatch` and `ready=false` with `reason=arg_contract_mismatch`, so a PBO older than the tools fails closed instead of matching on command names alone. `MCP_BRIDGE_VERSION` stays `"10"` (#94).

Others get `run_protected` (`box_protected` from `session_acquire_wait`) with `use_state`, `use_reason` and, for `idle` / `human`, `retry_after_s`, and `takeover=true` does not evict it. The launcher's rights survive `server_reload` but not a client reopen or a daemon restart (#135).

- For a project other than `DayZ_MCP`, `dayz_test_run` appends `@DayZ_MCP` to `extra_mods` when no spelling of the bridge is there and reports `extra_mods_defaulted`; `bridge_mod_missing` says so when the bridge sits in `base_mods`, which does not count (#143, #146).
- `pack-addon.ps1` packs the git-tracked `addon/` of `-Ref` (default `HEAD`) through a stage verified file by file against the commit, so uncommitted edits are not packed. `-Source <folder>` packs a plain folder instead, skipping editor backups and Markdown, and `-StageOnly` prints the staged files and their SHA-256 without packing. `pack-addon.ps1` and `deploy-addon.ps1` reset `PSModulePath` to the machine value (#62).

An existing registration, or an existence check (`claude mcp get` / `codex mcp get --json`) that is missing or unreadable, stops the script: re-register with `python tools/install_mcp.py --register`, or pass `-ReplaceExistingRegistration`. The installers' copies of the registry flags now include `--exec-audit-path`, and one test derives them from `server_cli`'s parser (#129).
- `dayz_test_run` refuses a closed Steam (no `steam.exe` running) with `error_code=steam_not_running` and a remediation that names the cause and the next step (start Steam and wait for its login, or retry with `auto_remediate_steam=true`), in validation, before any DayZ process starts. A running Steam with an invalid registration, and a host whose registry or process list cannot be read, still return `steam_session_stale`; the daemon-side gate keeps its codes (#90).

- `restore_gameplay` lists `render` in `not_verified` and no longer advises calling it again; `capture_screenshot` adds `render_frozen_signal` to `warnings` when a capture of two or more frames shows a single distinct frame (#65).

### Removed

- The internal bridge verbs `vehicle_drive` and `drive_probe_client`, which had no public tool; `vehicle_control` drives. An addon that still announces them shows them as `unmapped_announced_commands` (#68).

### Fixed

- An optional argument the caller omits no longer reaches Enforce as 0: an `object_anim` read no longer writes phase 0 (which had looked like car doors not holding a phase), and a partial `world_weather_set` no longer zeroes the other levels; `world_time_set` and `infected_drive` are covered too. The wire carries `<field>_set: true` beside each optional value, and the daemon refuses a value without its flag (#162).
- The daemon works from a Python 3.11 or 3.12 venv: its identity checks, the orphan reclaim and the legacy port reclaim accept the venv redirector's rewritten `argv[0]`, and the request parser fails closed as `json_undecodable` on nesting too deep for the 3.11/3.12 decoder (#112, #116, #126, #130).
- DayZ Tools on another drive: the bundle verifier finds DayZ Tools the way the builder does (`DAYZ_TOOLS_PATH`, then the registry, then the default), and the sealed launcher starts AddonBuilder from the sealed layout instead of a fixed `C:` path (#123, #128). On a fresh clone the launcher registry lock is created, the builder takes the Windows SDK paths from `tools/dependency-lock.json` instead of a fixed `C:` path, a bundle can be published onto another volume, and README's "Before the first test run" lists the host setup a first run needs (#114).
- `dayz_test_run(build=true)` through the native launcher no longer stops at `native_debug_gate_rejected:unapproved_debug_image`: in the AddonBuilder tree only, the debug gate admits a closed list of Valve-signed Steam client DLLs from the pinned Steam directory and Valve's `bin\x64launcher.exe` (#141, #152, #158).
- Fail-closed path checks (the daemon keyfile, host-config provenance, the installer's CLI path) accept an 8.3 short path to the same file instead of refusing it (#138).
- A session keeps its lease across `server_reload`: the handoff carrier follows heartbeats and lease-renewing commands (`lease_id` in `/enqueue` and lifecycle replies), a release or an invalidation clears it, and its I/O runs off the event loop. A reload that inherits an expired lease recovers without disturbing live or queued leases (#92, #119, #131).
- `session_release` of a token this client still held after a silent TTL answers `lease_expired` with `next_step=session_acquire_wait` instead of `lease_invalid`, and a heartbeat with an expired lease says it expired, even while a fence is up, instead of "token was never valid" (#77, #136).
- Remaining times (`expires_in_s`, queued tickets, grace `remaining_s`) never exceed their caps. `wait_for` never starts a probe after its deadline, and its wait for `tool_lock` counts against `timeout_s` (`timed_out` with `last_error=tool_lock_busy`) (#118, #127).
- In client mode, the readiness probe before a world read is capped by the caller's remaining deadline, so a slow probe no longer stretches the call (`da22937`).
- `dayz_test_stop` succeeds when DayZ is already gone instead of reporting `run_stop_failed` with `cleanup_degraded=true`; a run still alive after a failed stop still fails (#86).
- A lease grant adopts an ownerless `RUNNING_IDLE` or `UNRECONCILED` run whose owner is an empty string; it used to leave `adopted_run` null, and `dayz_test_stop` answered `run_not_adoptable` (#87).
- Manifest backups under `lifecycle-recovery-faults/backups/` stay bounded: the newest 200 plus every one a pointer or a fault names, with at most 128 removals per checkpoint (one host held 1.1 GB of them). A replace blocked by another reader retries for up to 1 s, and a backup a crash left incomplete is quarantined instead of stopping the daemon with `invalid_lifecycle_manifest_backup`. The doctor warns `MANIFEST_BACKUP_RETENTION_STALLED` and `MANIFEST_BACKUP_QUARANTINED` (#53, #63).
- When the MCP host is an MSIX app (Claude Desktop, Codex), the daemon is spawned through WMI, outside the app's registry virtualization, and the stdio Steam check reads the real `HKCU`, so a live, logged-in Steam no longer gets launches refused. `DAYZ_MCP_DAEMON_SPAWN_WMI=0` turns the WMI spawn off (#91).
- Starting a run no longer activates DayZ windows on launch, and the capture helper no longer opens a console window (#59). DayZ still takes the foreground for about 2.5 s once started, whatever the window's initial state; that is the game's own activation (measured 2026-09-30; see Known issues).
- Releasing a scripted `lookat` camera with `restore_gameplay` no longer freezes the client render: the view goes back through a FreeDebugCamera handoff, as vanilla's camera tools do, and the reply is posted when the handoff ends. `render_frozen_signal` also fires for a near-still frame pair (#167).
- `vehicle_control` applies brake and handbrake whatever the engine state and starts the engine only when `throttle` is above 0; a release restores the car's brakes-without-driver, as vanilla does (#170).
- `pipeline_inbox` no longer loses an entry, or the whole read, when a record holds U+2028, U+2029, U+0085 or an undecodable byte: records are split on the newline each one ends with and decoded one by one (#169).
- Concurrent inbox writers no longer lose or tear records: every append holds a cross-process lock on `feedback.jsonl.lock` (bounded at 10 s, then `inbox_busy` and nothing written), and a new id is checked unique under it (`inbox_id_collision` after 16 draws). Measured with the old code on Windows, six concurrent writers kept 255 of 300 records of about 1 KB. The id format, the size limits and the record fields do not change (#179).
- A daemon started from an interpreter other than `tools\.venv-mcp` prints one line naming both interpreters and exits 78 instead of a traceback and exit 1 (#184).
- A stop that races the reaper succeeds honestly (`stop_method: already_exited`) instead of `run_stop_failed` with the box free, and a DayZ launched by `start_run` survives a daemon crash between the launch and the manifest: a versioned `launch-intent.json` written before the launch lets the next daemon start record the orphan when exactly one process matches its argv hash, launch window and profile token (#185).
- `player_teleport` skips its occupant precheck when no client peer can answer it, instead of timing out on that probe (#76).
- `notify_players` with no connected player returns `{ok: false, sent: 0, error: "no_players"}` instead of `sent: 1` (#85).
- `object_inspect` echoes a malformed `type` in its `bad_args`, and a call with neither `type` nor `object_id` names both legal forms (#79, #84).
- `camera_set` restores gameplay when applying the camera fails after the controls were suppressed (#97).
- `capture_screenshot` reports a grab that never started as `capture_start_timeout`, apart from `capture_timeout` (#136).
- In DayZDiag, a client take to hands no longer throws a NULL pointer: the addon registers `PluginInventoryDebug`, which vanilla registers only when `IsDebug()` is true (#160).
- Fresh-launch `bridge_status.ready` no longer reports `server_poll_stale` from a dead pre-launch peer's leftover poll ages; the verdict is `binding_not_ready` until this generation's first accredited poll. The `ready` object comes first in the payload, publishes `stale_threshold_s` plus per-peer ages, and when `ready` is false names `next_step` (a public tool) before the ages (#77, #78).
- User-facing fence and lease errors name only public MCP tools (`session_status`, `bridge_status`, `session_acquire_wait`) and carry `next_step=`; they no longer cite internal `lifecycle_status` (#77).
- `dayz_knowledge_find` / `show` no longer route to `dayz_knowledge_prepare` when `can_prepare` is false; the error is `knowledge_pack_missing` / `knowledge_pack_invalid` with the install command, and `dayz_knowledge_status` publishes `install_command` (#77, #78).
- Untrusted clients keep the lease-free reads, `server_reload` and an owned `dayz_test_stop` when policy revalidation fails, including the stop of their own idle run; authority changes stay fail-closed (#30, #43).
- A bare `ClientRuntime` defaults to rejecting a stale policy (#37).
- Native job cleanup no longer fails with `native_job_cleanup_incomplete:active_zero_wait_timed_out` when the second wait already ran and no handle remains open (#40, #41).
- `python -m dayz_mcp.doctor` parses supervised registrations and `--exec-audit-path` again, so it checks the daemon instead of reporting `CONFIG_UNREADABLE`. The audit path is now compared as part of the daemon policy (#48).
- `pack-addon.ps1` passes `-packonly` when the source has no `.p3d`/`.paa`/`.rvmat`, matching the test worker so AddonBuilder does not binarize against every `config.cpp` under `P:\` (#57).
- `capture_screenshot` launches the grab without an inherited `PSModulePath`, so a Git Bash-poisoned module path cannot hide PowerShell cmdlets (#57).
- `vehicle_release` Abort autodumps a live trace before clearing it; stop the trace in a separate call, then release (#57).
- `player_teleport` refuses `occupant_client_seated` for a client-owned seated occupant so the server replica does not desync; one car per run, no get-out after `vehicle_get_in_client` (#57).

### Security

- DayZ, and Steam when dayz-mcp starts it, run with a whitelisted environment instead of the agent's, so the agent session's environment variables (API keys and other secrets) no longer reach those processes or their crash dumps (#144).
- The daemon checks the arguments of every whitelisted bridge verb against an ingress schema: the 16 verbs that accepted any payload (`world_spawn`, `camera_set` and `vehicle_control` among them) now refuse extra, missing or mistyped keys with `bad_args`, and a verb without a schema is refused (#117).
- Strings from identities or persisted state that reach MCP payloads (the registration stamp, daemon generations, stop-envelope state and reason, retired-run diagnostics) are echoed only when they match a closed shape (#46, #47, #66).
- Both bridges accept only an exact loopback REST URL, `http://127.0.0.1:<1-65535>/`, instead of anything that starts with `http://127.0.0.1:` (#173).
- `dayz_test_close` is denied inside playbooks, next to `dayz_test_run` and `dayz_test_stop` (#175).

### Known issues

- DayZ still takes the foreground for about 2.5 s when the server starts and again when the client starts. That is the game's own activation: starting the server minimized did not avoid it (#168, reverted in #180; measured 2026-09-30). Tracked as fade and 75e7; f298, which #59 fixed on the Python side, is closed.
- A `storage_1` rotation (another mod set used the same mission since the last run) resets the mission's world and characters, but `dayz_test_run` does not say so; the notice is only in the daemon's audit (`lifecycle_storage_rotated`) (c8c7).
- Reported by other sessions, not yet reproduced here: when AddonBuilder binarizes a project (`build=true` with `.p3d`, `.paa` or `.rvmat` files), binarize reads every `config.cpp` under the folder AddonBuilder passes as `-addon`, which can be the parent of the source or a temp root, so a broken `config.cpp` elsewhere fails the build (bf5c, 8cf9). A source reached through a Dokan-mirrored `P:` drive makes binarize exit at once (a97e). Publishing a rebuilt launcher bundle fails with WinError 5 or 32 while a live MCP client still holds the previous one (7672).
