## ROOT CAUSE
`inventory_attach` creates the attachment but never registers the created entity in the object-id registry that `world_spawn` populates (the registry itself lives elsewhere in `MCPBridge.c` — symbol NOT SHOWN), and no bridge command exists that deletes or unhooks an entity from a player's attachment slot; `object_delete` is scoped to world-spawn ids only.

## PROPOSED FIX
**Option 1 (recommended, smallest that closes the ticket's impact):**
- `addon/scripts/5_Mission/MCPBridge.c`, `inventory_attach` success path (after line 1975 / 1998): register `attachedItem` in the same id registry `world_spawn` uses and set `result.object_id` to that new id (instead of only echoing `command.args.object_id`).
- Extend the bridge's `object_delete` handler (NOT SHOWN) so that when the resolved entity is an inventory child (attachment/cargo), it is removed through the inventory API (e.g. delete via the parent's inventory / `DeleteAttachment`) rather than a plain world delete.
- Before: reply has `object_id` 0/absent, worn item unreachable. After: reply carries `object_id > 0`; `object_delete(object_id)` returns `ok` with `deleted=1` and the slot becomes free, so garment B can be attached.

**Option 2 (cleaner contract, larger):** add an `inventory_detach(slot, uid?)` server command — new branch in `MCPBridge.c`, entry in `loopback.py:SERVER_COMMANDS` + `_COMMAND_ARG_SCHEMAS`, mapping in `bridge_readiness.py:_BRIDGE_COMMAND_TOOLS`, a public tool in `server.py`, updated `SERVER_CAPABILITIES`/arg-contract hash, and a bridge-version bump. It deletes the slot's item (or drops it to the ground) and returns what it removed.
