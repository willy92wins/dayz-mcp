## VERDICT
OPEN_CONFIRMED — the supervisor code on main still clears in-flight ids only when the worker answers, never detects worker death, and never respawns, so a dead serving interpreter hangs calls forever and `server_reload` can only refuse with `drain_timeout`.

## EVIDENCE
- `tools/dayz_mcp/mcp_supervisor.py:307-315` — `_drain` loops solely on `while generation.inflight:` with a deadline; there is no check of `generation.process.poll()` or of any stdout-closed flag, so a worker that never answers makes it always return `(False, remaining)`.
- `tools/dayz_mcp/mcp_supervisor.py:216-221` — ids leave `generation.inflight` only inside `_pump_worker` when a response with a matching `id` arrives; a dead/hung worker never produces one.
- `tools/dayz_mcp/mcp_supervisor.py:231` — when the worker's stdout closes, the pump only logs `"stdout closed"`; it does not fail the remaining in-flight ids, set a dead flag, or trigger a respawn.
- `tools/dayz_mcp/mcp_supervisor.py:459-464` — `run` calls `start_worker()` once and then only relays host lines; nothing watches the worker or respawns it.
- `tools/dayz_mcp/mcp_supervisor.py:449-457` — `handle_host_line` admits every request id into `inflight` and forwards it; there is no `notifications/cancelled` branch, and the return value of `_send_worker` is ignored, so even a failed write leaves the id in `inflight` forever.
- `tools/dayz_mcp/mcp_supervisor.py:263-273` — `recycle` replies `{"error": "drain_timeout", "still_in_flight": [...]}` when `_drain` fails, exactly the observed refusal; it has no path that treats a dead worker as drainable.
- `tools/dayz_mcp/mcp_supervisor.py:166-173` — `_send_worker` returns `False` on a broken pipe, but no caller except `_heartbeat` (:332-335, which pops only its own id) acts on it.
- `tools/dayz_mcp/mcp_supervisor.py:18-21` — the module's own docstring states `Popen.pid` is the venv launcher, not the serving interpreter, matching the ticket's observation that the launcher stub can outlive the interpreter that holds the pipes.

## ROOT CAUSE
The in-flight set is garbage-collected only by worker responses. When the serving interpreter dies (the venv launcher stub may keep the `Popen` object looking alive), its stdout closes, the pump exits after one log line, and every id already admitted to `generation.inflight` stays there forever. `_drain` therefore always times out, `server_reload` always refuses with `drain_timeout`, and new calls are written to a stdin nobody reads (or fail silently with the return value ignored) and hang with no timeout.

## PROPOSED FIX
Recommended (smallest, in `tools/dayz_mcp/mcp_supervisor.py`):
1. In `_pump_worker`, after the `readline` loop (i.e. stdout closed), under `self._state`: pop every remaining id from `generation.inflight` (skip `_RESERVED_IDS`), `notify_all()`, and for each popped host id send a JSON-RPC error response to the host, e.g. `{"error": "worker_died", "generation": generation.number}` via the existing `_reply` shape (`isError: true`). This both unblocks `_drain` (which waits on `self._state` and sees `inflight` empty) and answers the host's hung calls instead of leaving them pending forever.
2. In `_handle_host_line`'s admission block (:449-457), if `_send_worker` returns `False`, pop the just-admitted id and reply `worker_died` immediately instead of leaving it in `inflight`.

Before: killed worker → calls hang indefinitely; `server_reload` → `drain_timeout` with `still_in_flight` forever. After: killed worker → each pending id gets an `isError` result `worker_died`, and `server_reload` proceeds through heartbeat (`send_failed` is already tolerated, :332-335), retire, respawn, and answers `{"status": "recycled", "generation": N, ...}`.

Optional second change (not required to close the ticket): in `handle_host_line`, on `method == "notifications/cancelled"`, pop `params.id` from `inflight` so host cancellations stop pinning the drain.

## SIZE / RISK
S. Main risks: (a) the pump's new error replies must not fire during a normal `_retire` — at that point `inflight` is already empty because `_drain` succeeded, but the heartbeat/replay ids must stay excluded via `_RESERVED_IDS`; (b) a worker that is hung but alive with open stdout is still not detected (only death via stdout-close is), so the fix covers the ticket's observed case but not every hang; (c) no bridge-version or persistence interaction — the change is entirely inside the supervisor process.
