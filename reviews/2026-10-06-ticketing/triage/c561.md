## ROOT CAUSE
`dayz_test_run`'s PASS criterion is "server booted and the DayZ_MCP bridge reached its poll loop"; it never reads the project mod's PBO entry list nor counts the project mod's own log lines, so a PBO binarized without `-include` (0 `.c` entries) produces a clean boot and a vacuous PASS.

## PROPOSED FIX
Recommended (smallest, additive):
1. In `tools/dayz_mcp/dayz_test_tool.py` (result assembly — NOT SHOWN) or a small new helper, after the run reaches readiness, scan the server `script_*.log` for lines prefixed with the project mod's tag and add `mods: [{mod, log_lines}]` to the `dayz_test_run` result; when the project mod's count is 0, add `warnings: ["mod_not_initialised"]` instead of failing. Log scanning can reuse the existing launch-log scan machinery (`log_tail.py` / `launch_logs.py` — NOT SHOWN).
2. Optionally (owner decision, since config-only mods are legal): before launch, list the project PBO's entries (reusing the listing logic of `tools/dev/pbo_provenance.py` — NOT SHOWN) and refuse with a new code `mod_pbo_has_no_scripts` when the project mod's PBO contains zero `.c` entries, with an override flag for legitimately scriptless mods.

Contract before/after: before — `dayz_test_run` returns `ok` with no per-mod evidence; after — the result carries `mods[].log_lines` and, for a scriptless/vacuous build, `warnings=["mod_not_initialised"]` (option 1) or a fail-closed `mod_pbo_has_no_scripts` refusal (option 2). Existing error codes and the storage-seal contract are unchanged.

## SIZE / RISK
S for option 1 (additive reporting), M for option 2 (PBO parsing + a new refusal code). Main risks: (a) false positives — attributing log lines to an arbitrary third-party mod requires a per-mod log tag that scriptless or quiet mods may not emit, so the `.c`-entry check is the more deterministic signal; (b) compatibility — a hard fail would break legitimately scriptless mods unless an override exists; (c) scanning cost is bounded only if it reuses the existing capped launch-scan path.
