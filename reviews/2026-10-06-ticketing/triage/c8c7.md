## ROOT CAUSE
`prepare_storage`'s `RotationResult` is returned to the daemon's launch-admission path (`process_lifecycle`), which reduces it to an audit row and returns `None`; no field of it is propagated through the sealed worker / start response into `_compact_result`, so the caller of `dayz_test_run` cannot learn that the world was reset.

## PROPOSED FIX
**Recommended (no re-seal needed):** surface the rotation through the status payload the tool already reads.
1. `tools/dayz_mcp/process_lifecycle.py`: in the rotation branch (~line 2793), retain the result per run (e.g. `self._storage_rotations[run_id] = result` or embed a `storage_rotation` object into the run's status record that `_execute_request` already fetches — the same channel `_steam_fields_from_status` reads at `dayz_test_tool.py:1843`).
2. `tools/dayz_mcp/dayz_test_tool.py`: add a `_storage_fields_from_status(status, run_id)` helper mirroring `_steam_fields_from_status` (1838-1849), and pass `storage_rotated` / `storage_backup` / `storage_reset_notice` into `_compact_result`, adding them to the dict at 1460-1510 **always present, null included** (same convention as `client_terminated` at 1478-1483, so consumers can rely on the keys).

Before: rotation → audit row only; `dayz_test_run` result has no storage keys. After: result carries `storage_rotated: true`, `storage_backup: "storage_1.modset-…"`, `storage_reset_notice: "mission_world_and_character_reset"` (all `null`/`false` when no rotation happened).

**Alternative:** the tool, after a successful launch, reads the audit `events.jsonl` row `lifecycle_storage_rotated` for its `run_id` and copies `storage_backup`/`notice` into the result. Avoids touching the daemon status contract but couples the tool to the audit file format and adds a read race with the audit writer.
