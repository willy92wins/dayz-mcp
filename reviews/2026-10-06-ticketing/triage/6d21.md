## VERDICT
OPEN_CONFIRMED — the Enforce bridge on main still hard-caps the door-component scan at 512 and returns `door_component_not_found` for any door whose view-geometry component index is ≥ 512, exactly as the ticket describes.

## EVIDENCE
- `addon/scripts/5_Mission/MCPClientBridge.c:450` — `protected const int ACTION_USE_DOOR_COMPONENT_CAP = 512;` the cap the ticket names is still present, with a comment (lines 446-449) explicitly stating that past the cap the result is `door_component_not_found`.
- `addon/scripts/5_Mission/MCPClientBridge.c:3808-3818` — the scan loop `while (componentScan < ACTION_USE_DOOR_COMPONENT_CAP && doorComponent < 0)` calls `doorBuilding.GetDoorIndex(componentScan)` only for indices 0..511; a door on component 876..1037 is never reached.
- `addon/scripts/5_Mission/MCPClientBridge.c:3820-3824` — when the scan ends with `doorComponent < 0` the handler returns `result.error = "door_component_not_found"`, matching the ticket's observed error.
- `addon/scripts/5_Mission/MCPClientBridge.c:3800-3805` — `door_out_of_range` is checked against `GetDoorCount()`, so the door index itself is valid; only the component lookup fails, confirming the failure is in the scan, not the index validation.
- `tools/dayz_mcp/server.py:6712-6718` — the tool description documents `door_component_not_found` as a possible door error, so the Python side passes the failure through unchanged (no compensating logic).
- `tools/dayz_mcp/loopback.py:1237-1248` — the `action_use_door` wire schema validates `door_index` 0..63 and has no notion of a component cap; nothing on the Python side masks or fixes this.
- NOT SHOWN: any engine/script API giving a building's view-geometry component count (would let the scan be bounded by the real count instead of a constant); also NOT SHOWN the `GetDoorIndex` implementation cost per call.

## ROOT CAUSE
`action_use_door` finds a door's view-geometry component by brute-force scanning component indices 0..`ACTION_USE_DOOR_COMPONENT_CAP-1` (512). Buildings whose door selections live on components with index ≥ 512 (the ticket's `Land_LF_RocaHeli` has 1230 components, window doors on 876..1037) are never matched, so the handler returns `door_component_not_found` even though `door_index` is within `GetDoorCount()`.

## PROPOSED FIX
Recommended (smallest): in `addon/scripts/5_Mission/MCPClientBridge.c`, raise `ACTION_USE_DOOR_COMPONENT_CAP` from 512 to a value above any real building's component count (e.g. 2048, comfortably above the 1230 the ticket reports as the generator's max). Behaviour before: `action_use(door_index=5, classname="Land_LF_RocaHeli")` → `ok:false, error:"door_component_not_found"`. After: the scan reaches component 876, `GetDoorIndex(876) == 5`, and the result echoes `door_index:5` with `component_index:876` and `started` per the existing contract. No wire-schema change (`loopback.py` and `server.py` untouched); the comment at lines 446-449 should be updated to the new cap. Rebuild/repack the PBO.

Alternative (larger): if a script API exposes the geometry's component count (not verified — see NOT VERIFIED), bound the loop by `min(count, cap)` and keep a safety cap; or extend `action_use_door` with an optional `component_index` argument so a caller can target a known component directly (requires schema changes in `loopback.py:1237-1248`, `server.py` validation, and the arg-contract hash bump).

## SIZE / RISK
S — one constant plus a comment, PBO rebuild. Main risks: (1) performance — the comment at `MCPClientBridge.c:446-449` notes one native `GetDoorIndex` call per index, once per command, so the worst case grows from 512 to 2048 calls on a not-found scan (still bounded and once per command); (2) bridge-version compatibility — the fix ships only in a rebuilt PBO, so an old addon keeps failing until repacked (the arg-contract hash is unchanged since no wire field changes, so `bridge_status` will not flag the stale PBO by itself).
