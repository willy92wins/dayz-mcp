## Hallazgos P2 en detalle

### R21C-F4-001 — versión de peer pegajosa → fail-open del handshake en downgrade

`loopback.py:93-94`:
```python
if version is not None:
    self._poll_versions[peer] = version
```
Secuencia: bridge 4B pollea `ver=4~1.29.163047` → estado `ok`. El juego se reinicia con un
PBO viejo (sin `ver=`) mientras el server MCP sigue vivo. `record_poll` recibe `version=None`,
el guard no sobreescribe → `_poll_versions` conserva `4~…`, `ensure_peer_allowed` sigue viendo
`ok` y las tools operan contra un peer que el contrato §5.2 define como `legacy_blocked` con
`--require-version` ON. `bridge_status` además miente (`version_state=ok` con poll age
fresco). Blast radius bajo (las tools 4B fallarían con `unknown_command` del bridge viejo; las
4A funcionan), pero es exactamente el estado que el flag existe para bloquear, y no hay test
que pinne la semántica (ver 013). Fix candidato: sobreescribir siempre (`self._poll_versions[peer]
= version` incondicional) — un poll sin `ver=` ES información ("este peer es legacy ahora").

### R21C-F4-002 — `/enqueue` bypassa allowlist + audit de exec

Con el flag ON, `whitelisted_commands()` añade `exec_enforce` al ingress HTTP genérico
(`loopback.py:82-86`); `_handle_enqueue` → `enqueue_command` solo valida whitelist de comando
y `args` dict. La allowlist de expresiones y el audit existen únicamente dentro de la tool MCP
(`server.py:514-516`). El bridge ejecuta incondicionalmente (`MCPBridge.c:711`). Resultado: un
proceso local con la key puede `POST /enqueue {"cmd":"exec_enforce","args":{"expr":"<arbitrario>"}}`
→ ejecución (engine-permitting) sin allowlist y SIN línea de audit. Mitigantes reales: flag
OFF por defecto, bind 127.0.0.1 + key (el key-holder local ≈ el operador), y GATE4B-LIM (la
ejecución real está rota en server headless hoy). Matiz de diseño: el plan §5.3 prometió
"doble gate (server-MCP + loopback)" — el loopback solo gatea el COMANDO por flag, no la
expresión; y G-2 exige conservar `/enqueue` para el harness. El hueco es coherente con la
letra de G-2 pero no con la intención audit-everything de §5.3. Fix candidato sin romper
harness: pasar la allowlist (y un audit hook) a `ServerState` y aplicarla en `enqueue_command`
cuando `cmd == "exec_enforce"` — chokepoint único para ambos ingress.

### R21C-F4-003 — audit de exec incompleto en caminos de fallo

`call_exec_enforce` (`server.py:148-156`) encola en :150 y audita "allowed" en :155.
(a) Si `audit_exec` lanza (OSError: disco lleno, `_audit/` no creable, lock de OneDrive), el
comando YA está en cola → el bridge lo ejecuta y el JSONL no tiene línea — registro forense
ausente exactamente cuando el entorno está degradado. (b) Si `enqueue_command` devuelve ≠200
(`queue_full` 429), se lanza ToolError en :152 ANTES del audit → intento allowlisted sin
rastro (no ejecutó, pero el audit-everything de §5.3 también cubre intentos: los denied se
registran). (c) `main_fn` viaja al bridge sin allowlist y no aparece en la entry
(`server.py:176-181`): dos invocaciones del mismo `expr` con `main_fn` distintos son
indistinguibles en el audit — `ExecuteEnforceScript(expr, main_fn)` invoca la función elegida
DENTRO del expr allowlisted, así que el poder extra es acotado, pero el registro queda
incompleto. Fix candidato: audit "attempt" ANTES de encolar + incluir `main_fn` + best-effort
(si el audit no puede escribirse con exec habilitado → ToolError SIN encolar, fail-closed).

### R21C-F4-004 — `year` sin rango en ambas capas

Python construye `"year": int(year)` sin check (`server.py:402-403`); `ValidateWorldTimeArgs`
valida month/day/hour/minute/multiplier pero nunca `args.year` (`MCPBridge.c:909-958`) →
`world.SetDate(year, …)` (`:632`) recibe cualquier int (−10⁵, 0, 999999) con comportamiento de
engine indefinido sobre el server vivo. Vía `/enqueue` omitiendo `year` → default Enforce 0 →
`SetDate(0, …)` con ok=1 silencioso. El plan §4.1 prometió "validación fail-closed de rangos
antes de aplicar" — `year` es el rango que ambas capas saltaron (el probe A/B del gate cubrió
2011/2026, no extremos). Fix candidato: banda pragmática (p.ej. 1970-2100) en ambas capas,
`bad_year`.

### R21C-F4-005 — instalación E3 rota fuera de `tools\`

`requirements-mcp.txt` = `mcp==1.27.2` + `Pillow==12.2.0`; el paquete `dayz_mcp` nunca se
instala en el venv (verificado mecánicamente: `Test-Path .venv-mcp\Lib\site-packages\dayz_mcp`
→ False) y `server.py:19` además importa el top-level `mcp_capture` desde `tools\`. El comando
de registro emitido (`install-mcp.ps1:98-104`, aplicado en `:125`) es `"<venv>\python.exe" -m
dayz_mcp …`, que solo resuelve cuando el cwd del proceso es `tools\`. El gate 4A pasó porque el
registro quedó en scope local de ese cwd; la ops note del propio gate ("re-registrar con `-s
user` … para uso global", `2026-06-10-fase4a-gate-ingame.md:50-52`) NO funciona: Claude Code
lanza el server con el cwd de la sesión activa → `ModuleNotFoundError: dayz_mcp`. Fix
candidato: cualquiera de (a) `pip install -e` de un pyproject mínimo, (b) wrapper `.cmd`/args
con `cd` al tools root, o (c) lanzar por path absoluto de un entry-script en vez de `-m`.
