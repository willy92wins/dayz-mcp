## Detalle

### R21-F2-001 — FAIL — path allowlist no fail-closed

El plan fija `fixture_jsonl` como ruta allowlist de misión y dice que fuera de allowlist debe ser `bad_args`: `DayZ_MCP_dev\plans\2026-06-08-fase2-observacion.md:109-117`. La implementación solo comprueba prefijo (`$mission:dayz_mcp/`) en `MCPBridge.c:731-736` y `StringHasPrefix` es un `Substring(0, prefix.Length()) == prefix` en `MCPBridge.c:1031-1039`. Después abre la ruta directamente con `OpenFile(validation.path, FileMode.READ)` en `MCPBridge.c:912`.

La API `OpenFile` acepta prefijos de filesystem como `$mission` y devuelve handle o `0` (`scripts\1_core\proto\ensystem.c:399-417`). Por tanto, el contrato fail-closed depende de una comparación textual débil, no de una allowlist real. Si el runtime normaliza `..`, una ruta como `$mission:dayz_mcp/../otro.jsonl` escapa. Incluso sin normalización, acepta cualquier fixture no especificado dentro del subárbol.

Fix sugerido: para fase 2, usar igualdad exacta con `$mission:dayz_mcp/telemetry_fixture.jsonl`. Si más adelante se necesitan varios fixtures, usar una tabla de nombres permitidos, no un prefijo libre.

### R21-F2-002 — FAIL — fixture vacío falsea éxito

`FGets` devuelve conteo de chars o `-1` si no hay más contenido (`scripts\1_core\proto\ensystem.c:483-501`). La implementación inicializa `readCount = FGets(handle, line)` y solo entra al bucle si `readCount >= 0` (`MCPBridge.c:925-926`). Si el archivo existe pero está vacío, el bucle no corre, pero el código cierra y devuelve éxito: `CloseFile`, `telemetry.found = true`, `result.ok = true` (`MCPBridge.c:947-950`).

Eso rompe el contrato de C2: el plan espera `line_count_read==2`, `last_valid.fixture_id=="fx2"`, `value==7.5`, `seq==1` (`DayZ_MCP_dev\plans\2026-06-08-fase2-observacion.md:117`) y clasifica `parse_error` como `ok=false` (`DayZ_MCP_dev\plans\2026-06-08-fase2-observacion.md:70-72`). Un archivo vacío es fixture inválido, no dato válido.

Fix sugerido: después de cerrar el handle, si `telemetry.line_count_read == 0`, devolver `ok=false` y un error estable (`parse_error` o `fixture_empty`).

### R21-F2-003 — WARN — parser acotado solo por input del caller

El default es 64 (`MCPBridge.c:13`, `MCPBridge.c:696`), pero si `args.max_lines > 0` se copia directo a `validation.max_lines` sin techo (`MCPBridge.c:738-746`). El bucle lee hasta ese valor (`MCPBridge.c:925-947`). Tampoco hay límite por longitud de línea: `FGets` reporta el count (`scripts\1_core\proto\ensystem.c:483-501`), pero la implementación no lo usa para cortar.

El plan prohibió `JsonFileLoader.LoadFile` por su lectura de hasta `READ_FILE_LENGTH=100000000` (`scripts\3_game\tools\jsonfileloader.c:1-3`, `DayZ_MCP_dev\plans\2026-06-08-fase2-observacion.md:116`). Esta implementación evita `LoadFile`, pero mantiene un camino de hitch síncrono si el caller manda `max_lines` enorme o una línea gigante. Como `telemetry_read` se despacha y postea en el mismo tick (`MCPBridge.c:579-598`), el impacto es degradación del sim, no solo respuesta lenta.

Fix sugerido: hacer `max_lines` fail-closed contra un máximo fijo y abortar si `readCount` supera un máximo de chars por línea.

### R21-F2-004 — WARN — radius/non-finite validation incompleta

`ValidateRaycastArgs` valida finite para `from/to` (`MCPBridge.c:620-630`), pero `radius` solo se comprueba con `< 0.0` y `> 0.0` (`MCPBridge.c:632-640`). En `object_at`, `radius` solo se rechaza si `<= 0.0` y luego se pasa a `GetObjectsAtPosition3D` (`MCPBridge.c:707-724`, API en `scripts\3_game\global\game.c:923-929`). El helper `IsFiniteFloat` solo cubre NaN (`value != value`) y devuelve true para cualquier otro valor (`MCPBridge.c:1046-1053`).

Eso deja dos clases de edge case: un NaN en raycast queda silenciosamente convertido al default 0.05, y un NaN/Inf/radio enorme en `object_at` puede llegar al engine. `RaycastRVParams` usa ese radio como radio del raycast (`scripts\3_game\global\dayzphysics.c:57`, constructor `:78-83`), así que también conviene capar el valor aunque `method=bullet` no lo use.

Fix sugerido: validar `radius` con `IsFiniteFloat`, endurecer el helper con comparación contra `float.MAX`/`-float.MAX`, y añadir máximos por modo (`scene_raycast` pequeño, `object_at` acotado).

### R21-F2-005 — WARN — JSON válido pero semánticamente incompleto puede pasar

El contrato del DTO es fijo: `MCPTelemetryFixtureLine { fixture_id, value, seq }` (`MCPMessages.c:87-91`; plan en `DayZ_MCP_dev\plans\2026-06-08-fase2-observacion.md:115-117`). El parser crea un solo `MCPTelemetryFixtureLine parsed` antes del bucle (`MCPBridge.c:924`), llama `serializer.ReadFromString(parsed, line, parseError)` (`MCPBridge.c:930`) y, si la sintaxis parsea, copia los tres campos sin validar contenido (`MCPBridge.c:941-943`). La API de `JsonSerializer.ReadFromString` reporta éxito/fracaso de deserialización, no valida semántica de campos requeridos (`scripts\3_game\gameplay.c:70-100`).

Resultado: una línea JSON sintácticamente válida pero incompleta puede terminar como `last_valid` con defaults o, por reutilización del DTO, con valores arrastrados de una línea anterior. El verdict solo cubrió JSON inválido sintácticamente (`C:\tmp\fase2-verdict.json:753-797`), no schema inválido.

Fix sugerido: crear `parsed` dentro del bucle y validar `fixture_id != ""` más la presencia/rango esperado de `seq`/`value` antes de aceptar la línea. Si falta algo, devolver `ok=false parse_error`.
