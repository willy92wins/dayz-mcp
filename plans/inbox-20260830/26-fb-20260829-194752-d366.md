## Compatibilidad, legacy y rollback

- Lectores legacy que sólo entienden schema siguen teniendo JSON completo; lectores nuevos verifican tres hashes y la línea `kind=commit` coincidente, y rechazan una publicación parcial.
- Primera publicación exige ausencia estable de cada canónico y no crea backups ficticios. `m23-receipts.jsonl` admite fichero ausente y legacy JSONL válido; líneas desconocidas se preservan byte a byte, no se reserializan.
- Antes del marker, recovery usa journal/backups para completar o restaurar sólo fingerprint, verdict, producers y schema; receipts nunca se restaura, trunca ni borra. Drift deja INCONCLUSIVE. Después del marker sólo acepta el conjunto nuevo si todos sus enlaces coinciden.
- Rollback es una transacción nueva: exige que el receipt histórico `commit` del schema objetivo siga presente; añade una línea `kind="rollback"` sobre el prefijo actual; restaura byte a byte fingerprint/verdict/producers y, último, schema. Nunca publica un backup de receipts ni consume/overwrite los backups fuente.
- Candidates, backups y journal no son autoridad pública. Una línea sólo acredita el commit marker vigente cuando es `kind=commit` y coincide en artifact_txid+schema hash.
- El banco de cinco fixtures es autoridad independiente producida por M13 y read-only para M23. Cambiar su contenido exige otra materialización/revisión M13; M23 nunca lo “actualiza” para hacer casar un wire/candidate nuevo ni trata wire↔candidate como sustituto del banco.
