## 3. Tramo 4A — wrapper MCP stdio (Python-only, CERO rebuild)

### 3.1 Estructura de código `[DESIGN]`

```
DayZ_MCP_dev/tools/
├── dayz_mcp/                  # package nuevo
│   ├── __init__.py
│   ├── __main__.py            # entry MCP stdio: python -m dayz_mcp
│   ├── server.py              # FastMCP app: 9 tools, mutex, lifespan
│   └── loopback.py            # lógica HTTP extraída de mcp_server.py (lib)
├── mcp_server.py              # SHIM: conserva nombre + CLI (--port/--keyfile) + los 5
│                              # endpoints (/enqueue /await /poll /result /set_poll_delay);
│                              # importa loopback.py
├── mcp_capture.py             # NO SE TOCA (D2) — se importa
├── mcp_client.py              # NO SE TOCA (harness)
└── requirements-mcp.txt       # mcp==1.27.2 (pin smoke-verificado)
```

- **Back-compat dura**: `run-fase3.ps1:256` lanza `tools/mcp_server.py` por path — el shim
  conserva nombre, CLI y comportamiento HTTP-only. El contrato real incluye
  **`/set_poll_delay`** (`mcp_server.py:79/:221-239`, usado por la suite de backpressure de
  fase 1 vía `mcp_client.py`): se preserva en la lib, HTTP-only, **NO se expone como tool
  MCP**, y gana un unittest directo (delay válido se aplica una vez al siguiente `/poll` con
  comandos; `ms<0`/`>5000` → `400 bad_ms_range`) porque los tests actuales no lo cubren
  (R22-F4-005). Criterio de gate: `run-fase3.ps1` y los unittests de `tools/tests/` siguen
  PASS sin tocarse.
- **Extracción, no reescritura**: `loopback.py` = mover `ServerState`/`Handler`/colas tal cual;
  el diff funcional del loopback debe ser ~cero salvo los puntos 3.2.

### 3.2 Cambios al loopback al extraerlo `[DESIGN]`

1. **Log sink parametrizado**: los `print()` actuales (`mcp_server.py:155/192/218/239/264`)
   van a stdout — embebidos en el proceso stdio corromperían el JSON-RPC. La lib acepta un
   logger; el shim HTTP-only mantiene stdout (harness parsea), el modo MCP manda a stderr.
   El SDK ya loguea a stderr (`configure_logging`, verificado).
2. **`last_poll_at[peer]`**: timestamp monotónico por peer en cada `/poll` (alimenta
   `bridge_status`). Campo nuevo en `ServerState`; sin cambio de contrato HTTP.
3. **Version check hook** (se ACTIVA en 4B): el loopback lee `ver=` del query de `/poll` si
   viene y lo guarda por peer; la validación la hace el server MCP (sección 5.2). En 4A los
   polls no traen `ver=` (bridge desplegado) → estado `legacy`.
4. **API encapsulada de `ServerState`** (R22-F4-002): el estado (hoy dicts compartidos +
   `threading.Lock`, `mcp_server.py:27-36`) se expone SOLO vía métodos sync breves con lock
   interno — `enqueue_command`, `take_result`, `status_snapshot`, `record_poll` — y el lado
   async los llama sin tocar los dicts directamente y sin sostener ningún lock a través de
   un `await`.

### 3.3 Server MCP (`dayz_mcp/server.py`) `[DESIGN]`

- `FastMCP(name="dayz-mcp", instructions=…)`; tools con `@mcp.tool(description=…)`;
  `mcp.run(transport='stdio')` (default verificado). Logs SOLO a stderr.
- **Arranque/parada**: lifespan levanta el loopback embebido vía wrapper `LoopbackServer`
  con `start()`/`stop()` (R22-F4-002): `start()` = thread daemon + `serve_forever` (igual
  que hoy, `mcp_server.py:258/:267`); `stop()` en el finalizer del lifespan =
  `httpd.shutdown()` + `server_close()` + `thread.join(timeout)` + jobs pendientes marcados
  cancelados — "daemon" solo evita bloquear el exit del proceso, no sustituye el cleanup
  determinista (tests/reload). **Lock de instancia E4**: si el bind del puerto falla (otra
  instancia o un harness corriendo) → el proceso muere fail-closed con mensaje claro. NO
  degradar a "cliente del otro proceso".
- **Puente tool→bridge**: la tool encola in-process en `ServerState` (mismo correlation-id
  y dict de results que hoy) y espera con polling async (`await asyncio.sleep(0.05)` hasta
  timeout por-tool, default 15 s; el patrón `/await` in-process). Timeout → `ToolError`
  con mensaje accionable (incluye liveness del peer, p.ej. "client peer last poll 34s ago —
  is the game client running?").
- **Mutex global E4**: `asyncio.Lock` compartido — toda tool que toca DayZ o la captura lo
  toma; `bridge_status` queda exenta (read-only, debe poder diagnosticar mientras otra tool
  espera). Necesario: el SDK despacha requests con `start_soon` (task group) — las tool-calls
  PUEDEN solapar (verificado en `mcp/shared/session.py` + `mcp/server/lowlevel/server.py`).
- **Errores de negocio**: resultado `ok=false` del bridge → `ToolError` (→ `isError:true`),
  nunca excepción de protocolo (patrón prior-art ya adoptado).
- **`capture_screenshot`**: importa `mcp_capture` (D2, sin tocar) y devuelve
  `Image(data=png_bytes, format='png')` o el dict ImageContent que ya produce
  (`image_content_from_png_bytes`, `mcp_capture.py:166`) — Codex elige la vía con menor
  adaptación, citando la firma real.
- **`bridge_status`** (host-only, sin Enforce): `{server_peer: {last_poll_age_s, queue_depth},
  client_peer: {…}, results_pending, version_state (4B), server_version}`.
- **Config CLI/env**: `--port`, `--keyfile` (mismos del shim), `--expected-game-version` (4B),
  `--require-version` (R22-F4-001: definido AQUÍ; default **OFF** mientras el bridge
  desplegado sea 4A/legacy, el install de 4B lo activa — §5.2/§6), `--enable-exec-enforce` +
  `--exec-allowlist <path>` (4B). La versión esperada del BRIDGE no es flag: es la constante
  `EXPECTED_BRIDGE_VERSION` del paquete (server Python y mod se shippean juntos; hacerla
  configurable solo invitaría a desalinearlos). Vía `claude mcp add … -- python -m dayz_mcp …`.

## 5. Seguridad E2 (consolidado)

### 5.1 Ya probado in-game (A4 — NO se re-litiga)
Key por request en query string (401 sin/mala key), whitelist de comandos (400 fuera), bind
forzado `127.0.0.1` (aborta si no). Caveat aceptado y documentado: la key viaja en query
porque `RestContext.SetHeader` solo admite Content-Type (`restapi.c:135-141`) — exposición
local mitigada por bind loopback; se documenta en el README de instalación.

### 5.2 Handshake de versión (nuevo, reemplaza el snapshot ERPCs)
- El server MCP guarda la última `ver=` vista por peer y deriva un `version_state` por peer,
  expuesto en `bridge_status` (R22-F4-001): **ok** (ambos componentes casan) · **legacy**
  (`/poll` sin `ver=`; solo tolerado con `--require-version` OFF — warning, tools operativas)
  · **legacy_blocked** (`/poll` sin `ver=` con `--require-version` ON → tools `ToolError`) ·
  **version_mismatch** (bridge-version ≠ `EXPECTED_BRIDGE_VERSION` **o** game-version ≠
  `--expected-game-version` → tools `ToolError` fail-closed SIEMPRE, independiente del flag).
- Transición: en 4A el bridge desplegado no manda `ver=` → instalar con `--require-version`
  OFF (estado `legacy` visible en `bridge_status`). El install de 4B (PBO con version-report
  ya desplegado) activa `--require-version` ON → `legacy` pasa a bloqueante. Razón del
  default por tramo: 4A debe poder correr contra el PBO ya desplegado sin rebuild (G-7),
  pero un F4 terminado no acepta peers sin versión.

### 5.3 `exec_enforce` gating (G-3)
- **OFF por defecto**: sin `--enable-exec-enforce`, la tool NO se registra (no aparece en
  `tools/list` — no invita al modelo a usarla).
- **Allowlist deny-by-default** (espíritu D-10): archivo JSON de expresiones EXACTAS
  permitidas (match estricto string-completo; sin regex/prefijos — superficie de bypass cero).
  Expr fuera de lista → `ToolError` + audit.
- **Audit log**: cada invocación (allowed Y denied) → línea JSON con timestamp UTC, expr,
  verdict, correlation-id, en `tools/_audit/exec_enforce.jsonl` (fuera del PBO). El loopback
  además exige que `exec_enforce` esté en su whitelist solo cuando el flag está ON
  (doble gate server-MCP + loopback).
